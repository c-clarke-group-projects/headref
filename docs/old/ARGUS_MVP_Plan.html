headref MVP Build Plan

An evidence based engineering team intelligence agent. This document is everything 2 people need to build the first stage without stepping on each other: architecture, implementation, ownership lanes, branching, rules, a single work log, and descriptive GitHub issues.

Keshan - Lane A Isiwara - Lane B Stage: MVP only Sources: GitHub + Jira Mode: read only Target: 3 to 4 weeks
Legend: SHARED both build together first LANE A Keshan (data and integrations) LANE B Isiwara (agent, api, ui) P0 must have for MVP
Team and lanes. Keshan owns Lane A (data and integrations). Isiwara owns Lane B (agent, api, ui). Merge policy: Isiwara's pull requests need Keshan's review and approval before merge. Keshan may review and merge his own work. Branches are kept after merge, not deleted.

1What we are building

headref answers a team lead question like "What is Keshan working on and is anything blocking him" using real evidence from engineering tools, not guesses.

The one rule that shapes every decision: headref is an evidence based decision support tool, not a surveillance or productivity scoring tool. Every answer is labelled as one of 3 classes:

Class Meaning Example
Verified fact Directly backed by a source Jira shows AUTH-245 assigned to Keshan, status In Progress
Inference Reasonable conclusion from 2 or more signals Keshan is likely working on AUTH-245 based on assignment, branch activity and an open PR
Unknown Cannot be established from sources Exact real time activity is unknown
Why this matters for the grade and the product: most student agents just call an LLM and print whatever it says. Ours separates facts from guesses, cites evidence, and admits what it does not know. That is what makes it look industry ready.

2MVP scope: in and out

Keep the load small. Do the deterministic, high value part first. Everything guessy or heavy is deferred.

In scope for MVP

  • GitHub read only (commits, PRs, reviews)
  • Jira read only (issues, status, assignee)
  • Identity graph (map GitHub user to Jira user to one person)
  • Canonical data model in Postgres
  • Deterministic member summary (assigned, in progress, open PRs, recent activity)
  • One LLM reasoning call over structured evidence
  • Evidence records + rule based confidence (HIGH / MEDIUM / LOW)
  • Conflict detection (Jira status vs GitHub PR state)
  • Simple web UI: team overview, member profile, evidence drawer
  • Seed script with a demo team and sample data

Out of scope (later stages)

  • Slack and Teams integration
  • Calendar integration
  • Any write actions (posting, changing tickets)
  • Numeric or percentage confidence scores
  • Vector search / semantic index
  • SSO, multi tenancy, full RBAC (use a simple login stub)
  • Human in the loop approval flows
  • Daily briefings, proactive notifications
  • Kubernetes, autoscaling, canary deploys
Golden rule for MVP: if a feature needs guessing or a write action, it is not in the MVP. We ship reliable facts plus one careful inference layer, and we ship it running.

The 5 stage agent flow (per request)

Stage Type Owner What it does
1. Plan Code B Decide which tools and time window the question needs
2. Build evidence Code B Call tools, correlate issue to branch to PR to commits, dedupe
3. Reason LLM B One Claude call over the structured evidence, forced to a schema
4. Validate Code + rules B Check each claim maps to real evidence, set confidence, flag conflicts
5. Respond Code B Format the JSON into the UI response with evidence and freshness
Security by design: the LLM in stage 3 never receives any write tool. Retrieved text (PR descriptions, Jira comments) is passed as untrusted data, never as instructions. This makes prompt injection unable to cause an action, at worst it affects one answer the user could already see.

4Tech stack (MVP lean)

Layer Choice Why for MVP
Language Python 3.11 Team standard, one language across api, agent and ingestion
Web / API FastAPI + Uvicorn Async, fast to build, auto docs at /docs
UI Jinja2 server side templates + a little vanilla JS No JS build step, lowest workload for 2 people. Upgrade to React later
Database PostgreSQL 15 (Docker) Single source of truth, structured queries
ORM + migrations SQLAlchemy 2.0 + Alembic Typed models, versioned schema
Validation Pydantic v2 Strict schemas for tools, evidence and LLM output
HTTP client httpx + tenacity Timeouts and retry limits on every external call
LLM Anthropic SDK (Claude) Native tool use and structured output. Needs an API key
Tests pytest + respx Unit tests, mock external APIs with recorded fixtures
Lint / format ruff + black One config, no debate, runs in CI
Container Docker + docker compose One command local run for the demo
CI GitHub Actions Lint and test on every PR
Cost note: the only paid piece is the Claude API key (pay per token) and, if you host it online later, a server. Local Docker demo is free. Keep the key in an environment variable, never in the repo. Agree a small spend limit before you start calling the API.

Deferred on purpose: Redis, vector DB, GitHub App, message queue. For MVP we use a read only token per integration and cache in Postgres. These are the correct upgrades for a later stage, not now.

6Two lane ownership

The split follows the data flow. Lane A owns everything that gets data in and makes it clean. Lane B owns everything that turns clean data into an answer and shows it. They meet at 2 agreed contracts: the database schema and the tool output shapes.

LANE A Keshan - Data and Integrations

  • A1 Identity graph model, resolver, and an unmatched queue for users that cannot be mapped
  • A2 GitHub client read only (PAT from env) plus ingestion into canonical tables
  • A3 Jira client read only (token from env) plus ingestion
  • A4 Read tools: get_assigned_issues, get_github_prs, get_commits, get_reviews, get_team_members. Structured output only
  • A5 Reliability: timeouts, retry limit, rate limiting, typed failures (see coding rules)
  • A6 Freshness: store source_updated_at and retrieved_at on every record

LANE B Isiwara - Agent, API and UI

  • B1 FastAPI app, config, health check, login stub, simple role check
  • B2 Orchestrator + planner (deterministic) that decides what a question needs
  • B3 Evidence builder that correlates issue to branch to PR to commits and dedupes
  • B4 Reasoning: the single Claude call with a strict output schema
  • B5 Validation + confidence + conflict detection (rules, no model needed for conflicts)
  • B6 Response + UI: team overview, member profile, evidence drawer, confidence badges, last synced time
Why this avoids blocking: Lane B does not wait for Lane A. B builds against the frozen tool contracts using the sample fixtures in seed/fixtures/. When A ships a real tool, B swaps the fixture for the real call. No one is ever stuck waiting.

7Interface contracts (freeze these in Sprint 0)

These are the handshake between the 2 lanes. Agree them together on day 1, write them as Pydantic models, and do not change them silently. If a contract must change, it is a shared decision plus a WORKLOG entry.

Tool output contract (example)

# app/schemas/tools.py  (SHARED - frozen in Sprint 0)
from pydantic import BaseModel
from datetime import datetime

class WorkItemOut(BaseModel):
    external_id: str            # e.g. "AUTH-245"
    title: str
    status: str                 # normalized: todo | in_progress | in_review | done
    assignee_user_id: int | None
    priority: str | None
    due_date: datetime | None
    source_updated_at: datetime
    retrieved_at: datetime

class PullRequestOut(BaseModel):
    number: int
    repo: str
    title: str
    state: str                  # open | merged | closed
    author_user_id: int | None
    linked_work_item: str | None  # e.g. "AUTH-245" parsed from branch/title
    updated_at: datetime
    retrieved_at: datetime

Insight response contract (what the API returns)

# app/schemas/insight.py  (SHARED)
class EvidenceItem(BaseModel):
    source: str                 # jira | github
    detail: str                 # "Jira AUTH-245 assigned to Keshan"
    observed_at: datetime

class Insight(BaseModel):
    claim: str
    classification: str         # fact | inference | unknown
    confidence: str             # HIGH | MEDIUM | LOW | UNKNOWN
    evidence: list[EvidenceItem]
    conflicts: list[str]        # human readable conflict notes

class MemberInsight(BaseModel):
    user_id: int
    likely_current_work: Insight | None
    assigned: list[WorkItemOut]
    blockers: list[Insight]
    risks: list[Insight]
    unknowns: list[str]
    last_synced: dict[str, datetime]   # {"github": ..., "jira": ...}
Rule: Lane A guarantees it returns WorkItemOut and PullRequestOut. Lane B guarantees it only reads those fields. As long as both keep their side, they can build in parallel and integrate cleanly.

8Conflict free working rules

  1. Contracts first. Freeze the schema and tool shapes in Sprint 0 before writing feature code.
  2. Own your folders. Do not edit files in the other lane's folders without a heads up in chat plus a WORKLOG note.
  3. Small PRs. One issue equals one branch equals one small PR. Aim for under 400 changed lines. Big PRs cause big conflicts.
  4. Pull before you push. Start every session with git pull --rebase origin main.
  5. Shared files are coordinated. Changes to models/, schemas/, config.py, migrations/ need a 1 line message to the other person first.
  6. Never 2 people in one migration. Only one person creates a new Alembic migration at a time. Say so in chat.
  7. Green before merge. CI (lint + tests) must pass. Isiwara's PRs need Keshan's review and approval before merge. Keshan may merge his own work.
  8. Daily 10 minute sync. Say what you did, what is next, what is blocked. Update WORKLOG.
  9. Fixtures over waiting. If you need the other lane's output and it is not ready, use the sample fixture and move on.

9Branching strategy

Trunk based with short lived feature branches. Simple and safe for 2 people.

  • main is always working and demoable. It is protected: no direct pushes, PR only.
  • Every task gets a branch off main. Merge back with a squash merge, then delete the branch.
  • Keep branches alive for hours or a day, not a week. Long branches drift and conflict.

Branch naming

type/<issue-number>-<short-desc>

10WORKLOG.md - the single work log

One file at the repo root records what each person did. The rule: the latest entry always goes at the very top, directly under the header, and each person only ever adds their own entries. Newest work is always read first. If a merge conflict appears, keep both blocks, it is never a real conflict.

Format

# headref Work Log

LATEST ENTRY ALWAYS AT THE TOP, directly under this header.
One block per work session.
Format: date | owner | lane | issue | what was done | next / blocked

---

## 2026-08-31 | Isiwara | LANE B | #18
Done:  Evidence builder correlates issue -> branch -> PR using fixtures.
       Added dedupe by (source, external_event_id).
Next:  Wire the real get_github_prs tool once #12 merges.
Blocked: waiting on final PullRequestOut shape (agreed in sync, unblocked).

---

## 2026-08-30 | Keshan | LANE A | #12
Done:  Built github_client with PAT auth, 10s timeout, 3 retries.
       Ingested commits + PRs into canonical tables. Added 4 unit tests.
Next:  Parse AUTH-xxx ticket id from branch names for linking.
Blocked: none.

---
Habit: update WORKLOG in the same PR as your code. A reviewer should see the code change and the log entry together. This is also your evidence of individual contribution for the assignment marking.

13Definition of Done

Architecture DoD (Sprint 0 exit)

  • Architecture diagram and data flow agreed by both
  • Canonical schema created, first migration runs on a fresh database
  • Pydantic contracts frozen and merged
  • Sample fixtures exist so Lane B can build without Lane A
  • Both can run docker compose up and reach the health endpoint
  • CI runs lint and tests on every PR

Implementation DoD (every task)

  • Code plus at least one unit test
  • ruff and black clean, CI green
  • Public functions have a docstring and type hints
  • No secrets in code, all read from environment
  • Every network call has a timeout and a retry limit, and logs attempted, returned, skipped
  • WORKLOG entry added in the same PR
  • Isiwara's PRs reviewed and approved by Keshan before merge; Keshan may merge his own work. Issue closed with Closes #n

MVP DoD (the release gate)

  • For a seeded demo team, headref answers "what is X working on and is anything blocking" with facts, one inference layer, evidence, and confidence
  • Conflict detection works (Jira status vs GitHub PR state)
  • Unknown is returned honestly when evidence is missing
  • A failed source is reported as unavailable, never as "nothing found"
  • Runs end to end via docker compose up and is demoable
  • The graded test scenarios pass (see section 17)
  • README explains setup and run in under 10 minutes

14Coding rules we maintain

  1. Small readable functions over clever ones. If a function does 3 things, split it.
  2. Every network call has a timeout and a retry limit. Log what was attempted, what came back, and what was skipped.
  3. Never commit secrets. API keys and tokens come from environment variables only. Check with a secret scanner in CI.
  4. Tools return structured data (Pydantic), never giant raw text blobs.
  5. The LLM never gets a write tool and never gets to change permissions, identity or policy.
  6. Retrieved content is untrusted. Jira comments, PR text and commit messages are data, not instructions.
  7. Deterministic software enforces auth, validation and filtering. The LLM only interprets and summarizes.
  8. Type everything and validate all inputs and outputs with Pydantic.
  9. Typed failures. Use error types like RATE_LIMITED, TIMEOUT, NOT_FOUND, UPSTREAM_ERROR so the agent can reason about missing data.
  10. Prompts are code. Store them as versioned files (reasoning_v1.txt), do not edit prompts loosely.
  11. Plain direct language in UI and docs. Numerals, no filler, no marketing tone.

17Testing (small but real)

Do not over test for an MVP, but cover the parts that decide correctness. Mock all external APIs with recorded fixtures so tests are deterministic.

What to test

  • Tools: success, timeout, 403 denied, 429 rate limited return the right typed result.
  • Evidence builder: issue links to the right PR and commits, duplicates are removed.
  • Confidence rules: 3 sources give HIGH, 1 weak source gives LOW.
  • Conflict detection: Jira In Progress plus merged PR raises a conflict note.

Graded scenarios to keep as a small test set

# Scenario Correct behavior
1 Clear in progress task with branch and open PR Likely current work, HIGH confidence, evidence listed
2 Jira In Progress but linked PR merged Conflict reported, not silently resolved
3 No GitHub activity but a Jira assignment Report Jira facts, mark code evidence as unknown
4 Injection text in a PR description Treated as data, no action taken, ignored as instruction
5 Jira source down "Jira unavailable", lower confidence, not "no blockers"
